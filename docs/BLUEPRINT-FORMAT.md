# DSP 蓝图串格式（模拟器实现说明）

本项目实现《戴森球计划》蓝图串的**双向**编解码（导入 + 导出）。格式细节不是照抄文档，而是对着**游戏真实导出的蓝图**逐字段反推并验证：

| 验证手段 | 结果 |
|---|---|
| 参考解析器的 ground-truth 蓝图（已知期望值：1 个区域 11×11、37 个建筑） | 完全一致 |
| 社区蓝图仓库 28 个真实蓝图 | 27 个成功解码；24 个 MD5F 校验通过 |
| 合成蓝图 编码 → 解码 → 再编码 | 逐字段一致（`test/codec.test.ts`） |
| MD5F 哈希 | 对游戏参考向量断言（`test/md5f.test.ts`） |

实现位置：[`src/engine/bp/`](../src/engine/bp/)（`codec.ts`、`md5f.ts`、`gzip.ts`）

---

## 一、文本信封

一次复制得到的字符串形如：

```
BLUEPRINT:<字段0>,<字段1>,…,<字段10>[,…]<描述>"<base64 负载>"<MD5F 十六进制>
```

**字段 0 是信封版本号，不是保留位**。两种真实存在的布局：

| 字段 | v0（经典） | v1（现行） |
|---|---|---|
| 0 | `0` | `1` |
| 1 | 图标布局 | **图标原型 id** |
| 2–6 | 图标 id ×5 | 图标布局 + 图标 id ×4 |
| 7 | 保留 `0` | 第 5 个图标 id |
| 8 | C# DateTime ticks | 同左 |
| 9 | 游戏版本 | 同左 |
| 10 | 短描述（URL 编码） | 同左 |
| 11 | — | 作者（URL 编码） |
| 12 | — | 自定义版本 |
| 13 | — | 属性标签（`;` 分隔） |
| 14 | — | 长描述 |
| 数据字段 | `"<长描述>,<base64>"` | `<长描述>"<base64>"` |

**关键差异**：v0 的 base64 在引号内、长描述之后（用逗号分隔）；v1 的 base64 紧跟在引号之后，**中间没有逗号**。

**描述字段不保证 URL 编码**，可能自带逗号——所以不能靠 `split(',')` 定位负载。实现做法：

1. 以最后一个 `"` 锚定哈希；
2. 同时尝试两种形状的负载切分；
3. 选出**真正以 gzip 魔数（`1f 8b`）开头**的那个，让形状判定自我验证而不是靠猜测。

```
负载 = 最后一个逗号之后的 token；若该 token 内含 '"'，则取引号之后的部分（v1）
```

## 二、二进制负载

全部为**小端**（little-endian）。

### 头部（29 字节）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u32 | `version` |
| 4 | i32 | `cursorOffsetX` |
| 8 | i32 | `cursorOffsetY` |
| 12 | i32 | `cursorTargetArea` |
| 16 | i32 | `dragboxSizeX` |
| 20 | i32 | `dragboxSizeY` |
| 24 | i32 | `primaryAreaIndex` |
| 28 | u8 | `areaCount` |

> 头部长度为 **29** 字节（28 字节字段 + 1 字节区域数），区域记录紧接着从偏移 29 开始。这一点由两重证据确认：
> 1. 只有从偏移 29 开始读，区域的 `index/parentIndex` 才是 `(0, -1)`、`areaSegments` 才是 200 这样的正常值；
> 2. `test/writer-bytes.test.ts` 把游戏导出的 ground-truth 负载解码后重新编码，头部+区域 43 字节与游戏输出**逐字节相同**。此前把区域数写成 32 位、或把头部当 32 字节，都会让之后的所有字段错位——这两处都曾真实存在并被这个测试抓出。

### 区域记录（每条 14 字节）

`index`(i8) · `parentIndex`(i8) · `tropicAnchor`(i16) · `areaSegments`(i16) · `anchorLocalOffsetX`(i16) · `anchorLocalOffsetY`(i16) · `width`(i16) · `height`(i16)

### 建筑段

```
u32 buildingCount
buildingCount × ( i32 pathNumber, 记录体 )
```

`pathNumber` 是记录布局判别符：

| pathNumber | 记录布局 |
|---|---|
| ≤ −102 | 最新（当前游戏） |
| ≤ −101 | 次新 |
| ≤ −100 | 较旧 |
| 其它 | 最旧：无 pathNumber，`index` 就是刚读到的那个数 |

### body 版本 1 的记录布局（无 pathNumber）

`bodyVersion == 1` 的蓝图里建筑记录**不带** `pathNumber`，而是定长 **61 字节**：

```
u32 buildingCount
buildingCount × 61 字节记录
```

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | i32 | `index` |
| 4 | u8 | `areaIndex` |
| 5 | f32×8 | 两个锚点 (x,y,z)(x2,y2,z2) + 2 个浮点 |
| 37 | i16 | `itemId` |
| 39 | i16 | `modelIndex` |
| 41 | i32 | `inputObjectIndex` |
| 45 | i32 | `link` |
| 49 | u8×12 | 保留 |

**这套偏移是实测的，不是推的**：

- `itemId` 在 **+37**：叠层风机文件读出 `2203`（风力涡轮机）× 6 + `1131` × 5；8687 栋的极地太阳能文件读出 `2205`（太阳能板）× 8672 + `1131` × 15。`modelIndex` 在 +39 读出 `53`/`37` 与 `55`/`37`。
- 位置块是**三个 float = 一个 Vector3**，第三分量在风机文件里呈**精确 8 单位等差**（`8, 16, 24, 32, 40`），正是「垂直叠层风机」应有的高度阶梯。
- 记录区是 61 的**精确整数倍**，且每条记录的 `index` 恒等于其序号，遍历正好停在缓冲区末尾。

### v1 变长记录：`41 + 4n`

另一个 v1 子集使用**变长记录**，长度满足 `length = 41 + 4n`（全语料 1649/1654 条精确成立）。头部 41 字节：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | i32 | `index` |
| 4 | u8 | `areaIndex` |
| 5 | f32×3 | 锚点 (x, y, z) |
| 17 | f32×3 | 第二锚点 (x2, y2, z2) |
| 29 | f32 | `yaw`（**度**，实测取值落在 [0, 360)） |
| 33 | f32 | `yaw2`（**度**） |
| 37 | i16 | `itemId` |
| 39 | i16 | `modelIndex` |
| 41 | 字节数组 `4n` | 尾部数据：**按字节紧密排列**，配方在**字节偏移 14** 处（`i16`）——见下 |

#### 尾部数组：配方在字节偏移 14

**它不是有意义的 i32 数组，而是按字节紧密排列的字段。** 早先版本把它整个读成 i32 并丢弃，
所以 27/28 个真实蓝图的速率表全空。

配方是尾部**字节偏移 14** 处的 `i16`，即 `tail[3]` 的高半部：

```ts
const raw = (tail[3] >> 16) & 0xffff;
return raw >= 0x8000 ? raw - 0x10000 : raw;
```

> **两个坑，都踩过：**
> 1. 写成 `(tail[3] << 16) >> 16` 会**恒为 0**——`0x00420000 << 16` 溢出 32 位。JavaScript 的位运算
>    是 32 位的，必须右移后符号扩展。
> 2. 把这四个字节当 `float` 读会得到 **32.0 / 8.0 / 0.03125** 这种看着很合理的数值
>    （`0x42000000` 正是 32.0f），很容易误判成某个系数。它就是配方 id。

证据（41,875 栋带尾部的建筑）：

| 检查 | 结果 |
|---|---|
| 制造机器解出有效配方 | **100%**——位面熔炉 504/504、电弧熔炉 26/26、制造台 Mk.II 16/16、Mk.I 14/14 |
| 非制造建筑（传送带/分拣器/发电/仓储/物流） | **100% 为 0**，从不出现配方 |
| 与蓝本文件名的一致性 | 星际熔炉三份蓝图名为 钛合金 / 钛块 / 高效金刚石，分别给出 66 / 65 / 61 = TitaniumAlloy / TitaniumIngot / DiamondAdvanced |

复现：`node --experimental-strip-types tools/verify-v1-recipe-offset.ts`

**尾部其余字段的语义仍未确定**，包括 `tail[2]`、`tail[4]`、`tail[5]`。
对传送带，`tail[5]` 已确认是**带上运送的物品 id**（实测 1006 煤 / 1112 金刚石 / 1004 钛石 /
1141 增产剂 Mk.I，全部是合法物品 id）。

#### `tail[1]`：对分拣器是「所依附的物体」，**不是行进方向**

`tail[1]` 的值随原型而异，不能当同一个字段用：

| 原型 | 观测 |
|---|---|
| 位面熔炉 | 全语料只有 3 个不同值（等于各自蓝图的 `建筑数 − 1`） |
| 分拣器 Mk.III | **1955 个不同值**（每个分拣器一个） |

对**分拣器**测下来它是一个**物体索引**：

| 检查 | 结果 |
|---|---|
| 解析到同一蓝图里的真实建筑 | **2037 / 2037（100%）** |
| 落在分拣器 3 格跨度内 | 1496（73%） |
| 位于**自身锚点** 1.2 格内 | **67.6%** |
| 位于**臂另一端** 1.2 格内 | **0.5%** |
| 沿臂方向（dot > 0.5） | 1.9% |

所以它指的是**分拣器自己那一端的物体**，而**不是**它搬运的方向——因此
**没有**被接成取料端/投料端。

> 顺带比较：v2 的 `outputObjectIndex` 在 2390 次引用里 **0 次**落在邻域内（p90 距离 175 格），
> 而 v1 的 `tail[1]` 有 73% 落在跨度内。**v1 的这个字段比 v2 的链接字段可靠得多**，
> 但它回答的是另一个问题（依附关系，不是物流方向）。

#### 两个被否定的假设（记下来免得重走）

1. **`tail[1]` 不是「组边界」**。它在 20+ 个蓝图里恰好等于 `建筑数 − 1`，看着像
   "last index of a group"；但逐建筑比对后只有 17.3% 等于所属区域的最大索引，
   67.5% 两者都不是。**否掉。**
2. **`tail[1]` 不是按原型统一的字段**。对熔炉有 3 个值、对分拣器有 1955 个值——
   把尾部当"i32 数组、每列一个含义"来读本身就不成立（见上：尾部是字节紧密排列的）。

复现：`node --experimental-strip-types tools/probe-v1-tail1-group.ts`

**元素个数 `n` 没有以任何整数形式存在头部里**，但它是**原型 id 的函数**（`tools/solve-v1-n.ts` 实测）：

| `n` | 原型 |
|---|---|
| 5 | 地基 1131、电力感应塔 2201、风力涡轮机 2203、火力发电厂 2204、太阳能板 2205、微型聚变发电站 2211 |
| 6 | 分拣器 Mk.I 2011、分拣器 Mk.III 2013、人造恒星 2210 |
| **5 或 7** | **传送带**（2001、2003）——同一个 id 会变长 |

传送带是唯一长度不唯一的原型：实测 628 条 2003 里 622 条 `n=5`、6 条 `n=7`；10 条 2001 里 3 条 `n=5`、7 条 `n=7`。`n=7` 的记录末尾多两个元素（`[..., 131072, 1006, 360]`），**推测是挂载了额外对象的记录**，但这一点**未证实**。

因为 `n` 逐原型可知，记录长度变成**一次短选择**而不是开放式扫描——实测该表只覆盖语料出现的 9 个原型，其余原型仍回退到不变量扫描，所以未测量的原型只是退回旧行为，不会失败。

**记录起点由三条不变量定位**（长度仍不能从内容直接算出，因为 `n` 不在记录里）：

1. `index`（+0）等于记录的序号；
2. `+37` 落在实测的建筑原型 id 窗口 `1100..5100`（由数据集实测范围 `1131..5003` 推出）；
3. `areaIndex`（+4）指向一个真实存在的区域。

并要求整段遍历**恰好消耗完记录区**。三条不满足即报不可解码。

尾部数组**现在被解释了一部分**：配方从**字节偏移 14** 读出（见上文），其余字段仍按原样保留在
`BlueprintBuilding.tail` 里供后续研究，**不假装知道**它们是不是对象引用。

**这一步曾经出过错**：第一版把窗口设成 `(0, 8000)`，虽然也解出 22 个文件，但语料一致性检查抓出 25 栋 `areaIndex` 越界、且部分记录的 id 是 `3 / 4 / 11 / 131`——那些是误判的记录起点。收紧到实测范围后越界归零，文件数不变。

**记录体（path102）字段偏移**

下表是**实测确认**的偏移（以 `pathNumber` 字段起点为 0）。确认方式不是自洽往返——自洽往返发现不了字段读错位置，因为垃圾值会从同一个错误偏移原样写回去。确认依据是**几何约束**：ground-truth 蓝图是 37 条传送带围成的闭环，把 `outputObjectIndex` 放在 +33 时，37 条里有 **34 条正好指向一格之隔的相邻传送带**，并串成完整闭环（`#1(10,0) → 0(10,1) → 2(10,2) → 4(10,3) → 3(10,4) → 5(10,5) → 25(9,5) → …`）；随机垃圾值做不到这一点。复现脚本：`tools/solve-endpoints.ts`、`tools/confirm-layout.ts`。

| 相对偏移 | 类型 | 字段 |
|---|---|---|
| 0 | i32 | `pathNumber`（判别符，新版为 `-102`） |
| 4 | i32 | `index`（建筑对象 id；分拣器用它引用两端） |
| 8 | i16 | `itemId`（建筑原型 id） |
| 10 | i16 | `modelIndex` |
| 12 | i8 | `areaIndex` |
| 13 | f32 | `x` |
| 17 | f32 | `y` |
| 21 | f32 | `z` |
| 25 | f32 | `yaw` |
| 29 | — | 朝向附加块（见下） |
| 33 | i32 | `outputObjectIndex`（`-1` = 传送带） |
| 37 | i32 | `inputObjectIndex` |
| 41 | i8 ×6 | `outputToSlot` `inputFromSlot` `outputFromSlot` `inputToSlot` `outputOffset` `inputOffset` |
| 47 | i16 | `recipeId`（`0` = 未设置） |
| 49 | i16 | `filterId` |
| 51 | u16 | `parameterCount` |
| 53 | i32 ×n | `parameters`（物流站参数等） |
| … | u32 | 记录尾部保留字段（实测恒为 `0`） |

传送带记录总长 = 53 + 4（尾部）= **57 字节**。

> **两个曾写错、现已修正的点**（任一个都会让整份蓝图错位）：
> 1. **传送带的朝向块是 4 字节，不是 8 字节**。多算 4 字节会让 `outputObjectIndex` 落在 `-1` 上，把真正的对象 id 当成 tail 的一部分。
> 2. **记录尾部还有 4 字节保留字段，必须消费掉**。不读它，每条记录只前进 53 字节，走到第 2 条就会读到 `pathNumber = 0` 而报错。
>
> 这两点合起来就是 `buildingRecordSize()` 里 `49 + 4(朝向) + 4(尾部)` 的由来；编码器、解码器与测试全部从这一个算式取值。

**`yaw` 不是规范化角度**。ground-truth 里 90° 的转向存为 `316.368`，180° 的转向存为 `15470`，也就是**未归一化的累积弧度**。因此解析器只拒绝不可能是角度的值（NaN / 非有限 / 超大），不按 `2π` 取模。

**`yaw` 也不总携带方向信息**：同一份蓝图里 32 条传送带的 yaw ≈ 0（量级 1e-4，属浮点噪声），只有真正转弯的 5 条有值。所以「yaw = 0」应理解为**未记录方向**而非「朝东」；`src/ui/glyphs.ts` 用 `YAW_EPSILON` 区分这两种情况，方向未知时画中性图案，而不是画一个自信的错箭头。

**朝向附加块的长度由 `itemId` 决定**：

| `itemId` | 附加长度 | 内容 |
|---|---|---|
| 2000 < id < 2010（传送带） | 4 | `tilt` |
| 2010 < id < 2020（分拣器） | 32 | `tilt` `pitch` 次级锚点 (x2,y2,z2) `yaw2` `tilt2` `pitch2` |
| 其它 | 0 | 次级锚点由游戏镜像主锚点 |

于是单条记录的字节数为 **49 + 朝向块 + 4×参数个数 + 4（尾部）**。这个算式由 `buildingRecordSize()` 统一提供，编码器与测试都从它取值，避免两处各写一遍而悄悄错开（历史上正是这样截断过蓝图）。

**记录之后可能有少量尾部数据**（ground-truth 蓝图末尾还有 5 字节）。`buildingCount` 是权威：解析到该数量就结束，不要求恰好消耗完缓冲区——游戏自身的解析器也是这么做的。

## 三、MD5F 哈希

**覆盖范围：从字符串开头（含 `BLUEPRINT:` 前缀）到数据字段的结束引号（不含该引号本身）。**

这是第二个极易写错的地方：遗漏 `BLUEPRINT:` 前缀会让**每一条合法蓝图**都被判为被篡改。修正后 27 个真实蓝图中有 24 个校验通过（其余 3 个经第三方工具改写，见下）。

MD5F 不是标准 MD5，差异有三处（依据 dspbptk 的 `DysonSphereMD5.Variant.MD5F`）：

1. **初始状态字**：`A=0x67452301, B=0xefdcab89, C=0x98badcfe, D=0x10325746`
2. **64 个轮常量中 8 个被改写**（索引 1、6、12、15、19、21、24、27），例如 `T[1] 0xe8c7b756→0xe8d7b756`、`T[15] 0x49b40821→0x39b40821`
3. 收尾追加 8 字节小端位长度

已知向量（`test/md5f.test.ts` 直接使用）：

| 输入 | MD5F |
|---|---|
| `""` | `84d1ce3bd68f49ab26eb0f96416617cf` |
| `"a"` | `f10bddaecb62e5a92433757867ee06db` |
| `"abcd"` | `fa27c78b6ec31559f0e760ce3f2b03f6` |
| `"Why are you doing this, Youthcat Studio?"` | `13424e12890a3f50a1f8567c464fff8c` |

用标准 MD5 会让导出的蓝图被游戏拒收——`test/md5f.test.ts` 里那条「必须与标准 MD5 不同」的断言就是为此存在。

## 四、DYBP 容器

```
"DYBP" | version(u8) | payloadLength(u32 LE) | payload
```

payload 的子编码随版本变化，解码按 **gzip → zlib → 未压缩** 依次尝试，并在 `payloadCodec` 中报告实际命中项；导出固定用 gzip。

## 五、覆盖范围与已知限制（如实记录）

### 已验证

| 能力 | 证据 |
|---|---|
| MD5F 变体（含 8 个改写轮常量） | 对游戏参考实现的 4 个已知向量断言通过 |
| 哈希覆盖范围（含 `BLUEPRINT:` 前缀） | 社区真实蓝图 27 个中 **24 个校验通过** |
| 文本信封 v0（12 字段、`"desc,b64"`） | 真实蓝图解析通过 |
| 文本信封 v1（15 字段、`desc"b64"`、作者/自定义版本/属性） | ground-truth 蓝图解析出 `LRFalk01` / `1.1` / 属性标签 |
| 头部 29 字节 + 14 字节区域记录 | ground-truth 蓝图解出 1 个 11×11 区域，`areaSegments=200`；与参考解析器期望值一致 |
| `u32 count + path 判别符 + 记录体` | 同上一份蓝图解出**恰好 37 个建筑** |
| **写入器与游戏输出逐字节一致** | `test/writer-bytes.test.ts`：把 ground-truth 蓝图解码后重新编码，**头部+区域 43 字节、建筑记录 2109 字节全部逐字节相同**（唯一差异是游戏在末尾多写 5 字节尾部数据） |
| 编码 → 解码往返 | 合成蓝图逐字段一致（含传送带/分拣器/物流站与参数数组） |

最后一条是本项目对「导出能被游戏加载的蓝图」最有力的证据：**它不是自洽测试**。自洽往返（自己写、自己读）无法证明写入器正确——两边可能共享同一个错误假设。逐字节对比游戏真实输出才可以。这个测试发现并修掉了 3 个写入器缺陷：头部长度、区域数写成 32 位、建筑数漏写。

### 一处残留不确定

游戏在记录区之后还会写 **5 字节尾部数据**（ground-truth 蓝图中为 `01 00 00 00 00`）。本项目的写入器**不写**这 5 字节，依据是：参考解析器与游戏自身都按 `u32 建筑数` 驱动循环、读完声明的记录数即停止，不校验缓冲区是否恰好耗尽；我们自己的解码器也不要求它。

**未在游戏内实测**（本机没有 DSP 客户端）。若你导出后游戏拒绝加载，这就是第一个要补的地方：在记录区后追加该尾部字段即可，`test/writer-bytes.test.ts` 的对比长度会随之变成完全相等。

### 尚未支持

社区蓝图仓库的语料大量由第三方工具（"仙术"系列等）产出，其负载在游戏原生格式之外**再套一层自有封装**。抽样 28 个真实蓝图的结果：

| 结果 | 数量 |
|---|---|
| 信封 + 区域解析成功，**建筑段无法读取** | 27 |
| 完全无法解析 | 1 |

也就是说：这类蓝图的**元数据、哈希、区域尺寸都能读**，但建筑记录读不出来。当前实现会**明确报告**这一情况（`declaredBuildingCount` 与 `buildings.length` 同时暴露，`tools/validate-real-blueprints.ts` 把它统计为 `metadata-only`），而不会返回错误的几何数据。

未继续攻关的原因很直接：该封装没有公开规范，继续靠统计猜测的收益低于风险（攻关过程中有两次"看起来对上了"其实是巧合，靠进一步验证才发现）。若需要支持，正确做法是拿到该工具的写出代码或规范。

**可靠性原则**：宁可报错，也不静默给出错误结果——`assertPlausibleIds()`、区域合理性校验（`areaSegments` 上界、`width/height` 为正）以及 `declaredBuildingCount` 都在服务这一条。
